# 简历与面试材料

项目名：基于 KuaiSAR 的搜索与推荐离线实验系统。

## 当前建议定位（v2）

传统搜推算法与可复现实验工程项目，不包装成线上工业系统。后续 LLM 推荐作为另一个独立项目，避免两份简历经历重复堆模型。

优先从以下四条中选三条；均明确离线/开发口径：

- 基于 KuaiSAR-small 约 1066 万条搜索/推荐交互建立可审计的数据管线，以全局时间切分、历史前缀特征和冻结用户状态控制泄漏；区分推荐曝光点击与实际搜索会话标签。
- 将 ItemCF 改造为分块构图、TopK 邻居与内存映射查询组件，支持共同用户支持度门槛、确定性融合及版本校验；热门＋ItemCF 在固定 2000 候选的开发验证 Recall 从 9.4229% 提高至 9.7700%。
- 在 575 万真实曝光上对照统计特征、可学习 ID/属性及匿名 caption 表示；同协议 ID/属性到内容增强的三种子开发 AUC 为 0.719850→0.722349，完成 GAUC、LogLoss 与候选列表指标的分离评测，不将曝光预测收益冒称线上 CTR 或端到端排序提升。
- 建立最佳检查点、学习率调度、完整轮断点恢复、数据/索引 SHA256 校验和独立指标重算；支持默认推荐与实验路由的命令行对照，未验证出稳定列表增量的复杂模型不进入默认。

最后双塔已完成真实验收：两组、主窗口各三个种子及较早窗口各一个种子，共 8 模型，完成 64 维索引导出、全库精确检索和固定预算对照。若简历强调双塔，可以写这些事实；历史输入使纯双塔开发 Recall@1000 均值 1.2954%→1.7866%，但融合未通过采用标准，不能写“超过 ItemCF / 全链路提升 / 已部署 ANN”。双塔设计与负结果用于面试展开，不强行挤入全部简历条目。

### 新版面试重点

1. 默认是近期热门＋改进 ItemCF 的直接 RRF，而不是最复杂的 DCN；排序模型保留为实验链路。
2. 全局 AUC / 用户 GAUC 衡量曝光样本预测，固定快照的周期观察点击覆盖是另一个任务；较高 AUC 不保证候选列表改善。
3. 解释固定总候选预算下的“召回新增 / 挤掉”两种效应，而不只展示并集变大后的 Recall。
4. 明确训练 loss 下降、验证选轮与数学上的收敛不同；预算结束与验证平台分别记录。
5. 词表中存在不代表检查点训练过；PAD、UNK、原始词 ID 0 和未使用 embedding 必须分别处理。
6. 旧最终测试已经被查看；新版结果是开发/回溯证据，不能再称新盲测、多重比较后的显著收益或线上提升。

## 历史 v1 面试问题

1. 为什么推荐 click 和搜索 click_cnt 不能直接混成同一 CTR 任务？搜索点击是在会话结果列表中，多个点击与零点击会话都要处理。
2. 为什么按全局时间切分？如何防止搜索与推荐间的未来行为泄漏？双塔历史严格早于目标，CTR 使用过去完整日期，测试固定 train 截止快照。
3. 冷物品为何限制召回？模型物品库只包含训练点击物品，新增视频不在库；应另设计具备可用时间约束的内容召回，不能提前拿测试物品拟合 ID。
4. 为什么 GAUC 比 AUC 低？全局用户点击倾向可提高 AUC，而组内排序提升较小；GAUC 还需要说明权重和有效组。
5. 为什么最复杂模型没有成为默认召回？实验表显示近期热门更适合当前静态短视频时间切分，复杂度不能代替验证结果。
6. 为什么搜索通道不能作为显著创新点？消融增益很小且单种子，门控与拼接接近，尚不支持强归因。
7. 为什么 CTR 更好但列表指标不一定更好？曝光分类与全库候选排序存在分布和目标差异，用户周期代理指标也不是实际请求指标。
8. 为什么不采用更快的 ANN？本机 IVF 达到所需重合率时更慢，保留精确；这是实现与硬件下的结果，不泛化成 ANN 无用。
9. 校准如何评估？同时报告 LogLoss、Brier 与 10 桶可靠性，常数概率可能 ECE 低但 AUC=0.5。
10. 如何证明结果不是挑出来的？先按验证集选择并保存 freeze.json，再运行测试；源码/模型摘要、候选和预测均保存，另行重算命中与概率指标。
