# 当前召回：实现与优化基线

## 范围

当前 V2 入口是 `src/v2/recommend.py` 的 `Backend.retrieve`，不是 V1 的双塔融合入口。
三路均只使用推荐训练期点击；搜索兴趣目前在精排特征中，不参与这三路召回。

```text
训练期推荐点击
  ├─ 全时点击次数排序 ─────────── Top1000
  ├─ 截止前24小时点击次数排序 ── Top1000
  └─ ItemCF：用户最近30个去重点击 → Top1000
            ↓
  去重、带权RRF融合（权重1/2/1，常数60）
            ↓
       最多2000个候选 → 粗排
```

### 热门两路

全时热门按物品训练点击事件数排序，近期热门只数训练截止前24小时的点击。
两者都不是CTR，也不按独立用户数计数；同一用户重复点击会累计。
两路对所有用户相同，在后端初始化时缓存。

### ItemCF

令 B[u,i]=1 表示用户u在推荐训练期点击过物品i；重复点击在共现矩阵中合并。
d[i]=sum_u B[u,i] 是物品i的点击用户数。

```text
N[u,i] = B[u,i] / sqrt(d[i])
sim(i,j) = (N.T @ N)[i,j]
         = 共同点击用户数 / sqrt(d[i] * d[j])
score(u,j) = sum_{i in H30(u)} sim(i,j)，自相似项置零
```

H30是训练截止前最近30个不同物品。查询种子等权，无时间衰减。
共现使用全部训练点击，不限于这30个种子。实现计算 `(h @ N.T) @ N`，没有显式存储约95万×95万的相似度矩阵。
查询后减去种子的对角自贡献；这不等于过滤历史物品，其他共现关系仍可能召回已点击物品。
当前允许重复交互，因此没有直接删除全部历史物品。
无训练点击用户的ItemCF路为空，由热门两路提供候选；不把热门兜底重复算成ItemCF贡献。

### 融合

`rrf(u,i) = sum_route weight(route) / (60 + rank(route,i))`。
同一物品每路只记一次，跨路得分相加，再截取前2000。
这是基于名次的融合，不是可解释为点击概率的打分。权重1/2/1是初始配置，尚不能称为已选优权重。

## 怎样读指标

事件Recall@K = 被每用户TopK列表命中的验证点击事件数 / 全部验证点击事件数。
同一用户反复点击同一物品会重复计入分母；每位用户只生成训练截止时的一份固定列表。
这是观察日志的覆盖指标，不是实际请求级CTR或完整相关性真值。

公平比较需要同一用户集合、同一个K、同一物品可用范围，并单列无训练点击用户。
K=100的单路不能直接与K=2000的融合比较。候选库条件Recall另外只以库内正点击为分母。

当前库是951625个训练期被点击物品。旧全量验证记录显示，库内正点击193639/354626=54.6037%。
因此45.3963%的正点击目标不在当前候选库；它们包含训练期未点击物品，不能全部称为新物品。
54.6037%是忽略每用户预算和可达性的宽松库覆盖上限，不是Top100应达到的目标。

## 第一轮优化需要回答的问题

1. 近期热门与融合在同一K下谁更好？每路1000和融合2000需要分开对照。
2. ItemCF命中多少热门之外的正例？看融合前独有命中和删除一路后的融合差值，二者含义不同。
3. RRF截断丢掉多少并集中已召回的正例？两路热门重叠是否挤压个性化候选？
4. 有训练点击用户与无训练点击用户的召回质量分别怎样？
5. 库覆盖受限和库内检索不足各占多少？扩库必须有截止前可用证据。

先保留当前配置作为基线。候选优化包括热度时间衰减、历史种子时间加权、活跃用户共现降权、搜索/推荐类别兴趣引导召回；需要逐项控制实验。
双塔需要在相同候选库与用户组上证明增量，不能因模型复杂就默认替换基线。

## 2026-10-16 全量验证结果

验证用户8495人、正点击事件354626次；有训练点击用户6085人，无训练点击用户2410人。以下全部使用同一验证窗口，没有访问测试标签。

| 方案 | 事件Recall@100 | 事件Recall@1000 | 事件Recall@2000 |
| --- | ---: | ---: | ---: |
| 全时热门 | 0.9362% | 4.9176% | 7.2056% |
| 近期热门 | 1.6536% | 6.8486% | 9.4229% |
| ItemCF（最多1000） | 0.2642% | 2.4626% | — |
| 当前三路RRF融合 | 1.5256% | 6.2646% | 8.0448% |

热门两路的2000列是独立扩展到2000物品的等上限对照，当前服务仍是每路1000。当前融合平均1845.68物品，近期热门对照填满2000，故2000列差异含容量利用率差异；1000列是同数量对照。

三路当前Top1000并集在截断前平均2119.87物品，命中29335次正事件（Recall8.2721%）；RRF截取最多2000后命中28529次（8.0448%），截断损失806次。近期热门独立Top2000命中33416次（9.4229%）。因此单纯重排现有候选池无法达到这一更强基线的覆盖，需要调整路内取量和候选来源。

当前路内候选池中的独有正事件：全时热门2008次、近期热门8207次、ItemCF2555次。删除ItemCF后融合命中减少1749次，但候选均值也从1845.68降到1510，不能将该差值全部归因为等数量下的算法提升。独有事件覆盖证明互补性，不证明固定预算下应分配多少名额。

对有训练点击用户，Recall@1000：近期热门5.4940%、ItemCF2.9441%、当前融合4.8467%；无训练点击用户：近期热门13.7773%、ItemCF0%、当前融合13.5169%。用户分组之间难度不同，不能直接把高低归因为冷启动策略优劣。

### 优化顺序

1. 固定2000候选上限，增加近期路供给，比较近期保护配额、RRF权重与去重补足；同步看100/400/1000/2000的Recall和ItemCF独有覆盖。当前近期热门Top2000是已验证更强的候选生成基线，但尚未验证其后续排序效果。
2. 对ItemCF分别验证历史种子时间衰减、活跃用户降权和训练共现窗口。一次只改变一个因素。
3. 增加搜索/推荐类别兴趣引导的召回，对照全局近期热门，分有无搜索历史报告增量。
4. 同一用户、候选库和K下复核双塔的属性、历史与负例策略，再决定是否接入。
5. 物品库扩展先纳入截止前已曝光但未点击物品；进一步新物品召回需要可验证的时间可用性。

原始报告：`experiments/v2_recall_diagnostics_valid_all/metrics.json`。本轮11项针对性测试通过；全时热门和全历史ItemCF的Top100命中数与旧独立报告完全一致，用户分组加总、命中单调性、库内Recall范围及融合截断损失核验通过。
