# ItemCF 索引化改造

## 目标与边界

把原来的每请求用户—物品矩阵计算，改为离线建表、版本化发布、请求时读取有限邻居的召回组件。本轮不训练双塔或其他神经模型。

实现提供本机可验证的组件与实验；分布式任务调度、增量共现更新、远程KV服务、并发SLA与线上A/B仍需要后续建设。

## 离线与查询分工

```text
rec train正点击（timestamp < cutoff）
  → user-item去重，保留最新点击时间
  → 时间窗口＋单用户最近物品上限
  → 可选活跃用户降权、图内时间衰减、热门度归一化
  → 分块共现计算＋可选共同用户数门槛/置信度收缩
  → 去对角，每物品只保留TopL邻居
  → .npy数组＋SHA256清单＋版本号
  → 同卷暂存目录构建完毕后原子重命名发布

用户ID / 请求前的最新行为历史
  → 最新H个去重种子＋可选时间衰减
  → 读取各种子的TopL邻居
  → 累加候选贡献＋显式过滤＋确定性TopK
  → item_id、score、shortfall、索引版本、可选种子解释
```

索引使用只读内存映射，查询路径没有数据库读取、神经模型调用或全量用户—物品矩阵乘法。批量接口是惰性迭代，避免一次保留所有用户的结果；它不隐含并行执行。

## 算法定义

令B[u,i]表示截断后用户是否点击物品i，n[u]是截断前、窗口内的去重历史长度。
可选行为权重e[u,i]=2^(-(cutoff-t[u,i])/graph_half_life)。未启用图衰减时e=1。

```text
w[u] = 1/log(2+n[u])，启用IUF时；否则为1
d[i] = sum_u B[u,i] * e[u,i]
S[i,j] = sum_u B[u,i]B[u,j]w[u]sqrt(e[u,i]e[u,j]) / (d[i]d[j])^alpha
```

alpha=0.5且不启用额外权重时是二值余弦；降低alpha会减弱对热门物品的惩罚。该参数通过开发验证比较，不能事先断言越低越好。
可选置信度收缩为S *= common_users/(common_users+shrinkage)，也可设置最少共同用户数。之后清除自相似，每行只保留TopL；逐行截断使索引成为有向邻居表。

请求时score(u,j)=sum_i 2^(-(request_time-t[u,i])/query_half_life)*S[i,j]；关闭衰减时种子等权。
原始共现与推理分数都不是点击概率，不用未曝光物品伪造CTR负标签。

## 可控成本与一致性

- 单用户建图历史上限约束重度用户共现展开；IUF仍根据截断前活跃度计算。
- 分块构图，内存中不保存完整物品×物品矩阵。索引数据为int32邻居位置、float32相似度，原始物品ID使用int64。
- 查询最多访问H×L条边，再去重、累计和选TopK。文件大小由目录规模和L决定；内存映射文件大小不等于进程常驻内存。
- 索引保存数据manifest摘要、截止时间、参数、构建代码摘要和各数组摘要。加载核对版本、SHA256、形状及数据快照；拒绝早于图截止时间的请求。
- 新目录先完整构建、关闭写映射，再发布；不覆盖已发布目录。构建失败的临时目录保留，不能作为ready索引加载。
- 接口支持请求前新行为，严格过滤同时刻及未来行为；同物品保留最新一次，未知物品显式记录。固定历史评测不使用验证行为更新种子。
- 默认允许重复交互；exclude_items可传完整业务排除集。exclude_history排除接口所持有的历史：传入历史时覆盖全部有效历史，默认快照只保存最近H个种子，不能冒充全量终身已看集合。
- 冷用户无历史时返回空路与原因，不在ItemCF内部混入热门兜底；用户有有效新历史时可不依赖训练用户ID。
- 相同分数按原始item_id打破并列。解释接口列出贡献最高的种子；约束或邻居不足时返回shortfall。

## 第一轮真实实验：压缩收益与质量损失

同一951625物品目录、8495验证用户、354626正点击事件。21,568个训练点击用户，去重历史中位数48、P95为547、最大3549。
历史上限200保留1699190/2857896条去重边，317549个物品在压缩图中没有可用邻居。

| 方案 | Recall@100 | Recall@1000 |
| --- | ---: | ---: |
| 原全历史精确ItemCF | 0.2642% | 2.4626% |
| 上限200＋每物品100邻居，余弦 | 0.1057% | 0.8592% |
| 同预算，加入IUF | 0.0883% | 0.6534% |
| IUF＋1天查询半衰期 | 0.0939% | 0.6889% |

匹配256名有训练点击验证用户、相同Top1000、预热后重复3次：原查询P95约27.93ms，压缩余弦约0.444ms。
这是CF自身的单进程CPU查询测量，不含网络、并发和索引构建/加载；不据此宣称服务QPS或生产SLA。
该压缩方案质量下降明显，不能仅凭加速替换默认召回。IUF在本轮也没有正收益。
原始结果：`experiments/itemcf_index_valid_all/metrics.json`。

第二轮保持当前数据的全部去重历史（上限4000，大于本次观测最大3549），比较L=100/300/1000，再在相同L下比较热门度归一化与查询衰减。此上限是本次资源与数据设置，并非工业统一标准。

## 运行与接入

本轮验证环境为Windows、Python 3.12.14、CPU PyTorch 2.8.0；依赖快照见`requirements-v2-cpu.lock`。代码使用Python 3.10以上的类型语法。先按仓库说明取得官方数据并构建ready数据库。ItemCF独立建图、查询和评测不依赖双塔权重。
Git仓库只包含代码和汇总报告，不包含ZIP、SQLite、特征缓存、模型或邻居索引。报告存在不代表本机模型可加载。若需四阶段演示，还需粗排/精排权重及匹配的特征缓存；`scripts/run_v2.ps1`可在另选机器上准备这些资源，不必在本机重新训练。
新克隆运行`run_v2.ps1`会把模型和新验证结果写入忽略的`artifacts/v2_runtime`，生成`cascade.json`；ItemCF级联配置中的coarse_model/fine_model应指向该配置里的实际权重路径。本机现有`experiments/v2_*/model.pt`路径仅用于已完成的本地演示。

```powershell
# 完整可复现构建和全量验证；新RunName保留既有实验
./scripts/run_itemcf.ps1 -RunName itemcf_reproduce

# 单独构建、查询和解释
./.venv/Scripts/python.exe -m src.itemcf_index build --config configs/itemcf_index_balanced.json --out artifacts/itemcf_new_version
./.venv/Scripts/python.exe -m src.itemcf_index query --index artifacts/itemcf_new_version --user-id 20235 --k 20 --explain

# 已有索引上的单因素开发消融
./.venv/Scripts/python.exe -m src.itemcf_evaluate --variants configs/itemcf_ablation_full.json --out experiments/itemcf_new_evaluation --benchmark-users 256 --repeats 3

# 使用本机已构建的折中索引进入四阶段链路
./.venv/Scripts/python.exe -m src.v2.recommend --config configs/cascade_v2_itemcf_index.json --user-id 20235
```

V2级联配置可添加itemcf_index路径、itemcf_query_half_life_days覆盖值和itemcf_neighbor_limit查询邻居数；加载索引后跳过旧共现矩阵构建。
同一文件目录可被多个进程只读映射。版本切换通过加载新的不可变目录完成，当前没有实现服务级无损热切换。

参考：[Amazon关于item-to-item推荐的说明](https://www.amazon.science/the-history-of-amazons-recommendation-algorithm)、[SARPlus的预计算相似度缓存与内存映射设计](https://github.com/recommenders-team/recommenders/blob/main/contrib/sarplus/README.md)。本项目的参数和效果需要自己的实验支撑。

## 最终交付与第二轮验证

第二轮使用完整训练去重边2857896条、同一951625物品目录；历史上限4000在当前数据上没有实际截断。无邻居物品仅160个。

| 配置 | Recall@100 | Recall@1000 | 查询P95（ms） |
| --- | ---: | ---: | ---: |
| 原全历史精确ItemCF | 0.2642% | 2.4626% | 27.127 |
| 完整历史、余弦、L=1000 | 0.2374% | 1.2732% | 1.763 |
| 完整历史、alpha=0.25、L=300，折中档 | **0.6068%** | **3.4665%** | **0.861** |
| 完整历史、alpha=0.25、L=1000、查询半衰期1天 | 0.6164% | 3.5905% | 1.785 |

所有质量指标为同一8495用户开发验证，正点击分母354626，纯CF路没有热门兜底。时延均为同种子选择的256名有训练点击验证用户、相同Top1000、预热后3次重复、单进程CPU查询。原版与折中档时延来自最终导出索引的同轮对照，其余来自第二轮消融，不能把不同实验轮次的微小时延差当作确定优势。

折中档相对原版Recall@1000提高约40.8%，绝对增加1.0039个百分点；两者均无兜底。折中档平均663.42个CF候选，原版约697.12个，增益不是来自返回更多CF候选。
保持热门两路、RRF权重1/2/1和2000候选上限后，融合Recall由8.0448%升至8.3271%；热门两路之外的CF独有正事件由2555升至3224。
融合仍低于近期热门独立Top2000的9.4229%，且没有验证最终Top20或线上收益。

同L=1000、同完整历史下，alpha从0.5降到0.25，Recall@1000由1.2732%升至3.5821%；按用户bootstrap的探索性95%差值区间约为[2.1726,2.4444]个百分点。
这支持本数据、本裁剪方式下减弱热门度惩罚有益于观察点击覆盖；不能直接推导个性化强度、长尾价值或其他数据上的效果。
在该配置上增加1天查询衰减，Recall@1000仅多30次命中，探索性区间包含0，故折中档保持等权历史。IUF也未进入交付折中档。

折中档每个物品最多300个邻居，最多展开30×300=9000条边。实际交付索引约2.14GiB，通过只读内存映射访问；1000邻居高召回档约7.10GiB。这是磁盘/缓存、查询成本与覆盖效果之间的显式取舍。
折中版本由大索引逐行精确截取后不可变发布，逐用户审计确认全部8495用户的Top100/1000命中向量与父索引L300完全一致；也可用`configs/itemcf_index_balanced.json`直接构建。
导出耗时不代表完整构图耗时；metadata另外记录父图构建耗时和版本。

交付入口：

- `configs/cascade_v2_itemcf_index.json`：折中档，已真实运行2000→400→80→20；索引版本为`2a04bafafdce84e2c413`。
- `configs/cascade_v2_itemcf_quality.json`：1000邻居、1天查询衰减的开发高召回档，不称为全局最优。
- `experiments/itemcf_index_full_valid_all/metrics.json`：9组消融、逐组指标、用户bootstrap与重复时延。
- `experiments/itemcf_balanced_valid_all/metrics.json`：实际导出版本的全量验证与重复时延。
- `experiments/itemcf_balanced_valid_all/audit.json`：逐用户命中向量、分母、融合和版本审计。
- `experiments/itemcf_balanced_demo.json`：真实四阶段接口输出。

全部59项测试通过，包含时序、二值去重、稠密公式对照、时间加权、置信度收缩、邻居预算、导出/直接构建一致性、校验拒绝和级联集成。PowerShell脚本语法及拒绝覆盖既有实验的保护检查通过。所有结果属于同一开发验证窗口，尚需独立保留窗口复核。

## 尚待分析的算法问题

这轮完成的是索引组件和开发验证改善，算法尚未最终验收：

1. 单共同用户支持的边可能获得高分。已核对的用户20235有50个训练点击物品、查询用最近30个；其CF第一名641055是更早点击过的物品，若干贡献边仅有该用户一人支持。需要按共同用户数分桶、检验目标用户自身共现贡献，并比较支持度门槛和置信度收缩。
2. 默认允许重复交互。需要分开报告重复点击和新物品发现的覆盖，再决定已看排除策略；直接过滤全部历史会改变现有评测目标。
3. 仍需另一个时间窗口复核，并在固定候选预算下检验ItemCF与热门路的取量、互补性及最终排序收益。
